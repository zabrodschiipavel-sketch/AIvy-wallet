Loan-screen create/edit writes are integrated at `0e3ac27cf`. `LoanWriteCommand` joins the loan or record, converted record amounts, loan category and associated financial operation in one Room transaction. Category creation uses raw DAOs inside that boundary; cache invalidation and observers run after it, so no category event exposes an uncommitted graph. Cancellation and write failures propagate. Creators return a confirmed result, with a separate warning if only the subsequent refresh fails. The modal awaits that result, retains its draft on write failure, blocks repeated saves and edits while saving, and ignores disposed/replaced modal completions. Form values are captured before launching the write. The existing account controller behavior is shared through a generic controller; its nine regressions still pass.

The command rejects non-finite/non-positive principal amounts, invalid parent/record ownership, missing/deleted rows and new links to archived accounts. Existing history on the same archived account can be edited. Record conversion uses a checked parent snapshot; the loan-associated operation is re-read inside the transaction instead of resurrecting a ViewModel snapshot. The new Room cases inject SQLite failures at each creation write, failures after compound edits and tag-link deletion, cancellation and reentrant observer reads. Both Android APIs passed all 92 tests; JVM, XML, R8 and UI evidence is preserved under `build/mcp-roadmap/loan-write/checkpoint-0e3ac27cf/` and the adjacent logs/scripts.
